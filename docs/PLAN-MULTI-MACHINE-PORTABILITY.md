# Plan: three-phase workflow — bench here, run everywhere, port by RAM tier

**Status**: draft — implementation starting
**Created**: 2026-07-04

## The three phases (why this doc exists)

This project already does phase 1 well and has phase 2 built, but phase 3 is
only a hand-written doc, not a tool. Naming the phases so README/TASKS can
point at them precisely:

1. **Bench (this machine)** — `bin/bench` runs the full matrix: every
   (runtime × model × adapter × case), graded and timed. Output: `results/*/results.csv`.
   Done, mature (decomposed checks, difficulty tiers, trials/medians).
2. **Run (any machine, once winners are known)** — `llmrun <agent>` (built via
   [bin/build-llmrun](../bin/build-llmrun), see
   [PLAN-CLI-UNIFICATION.md](PLAN-CLI-UNIFICATION.md)) is the standalone
   dotfiles binary that does real work with the model/adapter combo the bench
   picked. Done — `llmrun runtime`/`model`/`agents config` all implemented and
   tested against this machine's lms/ollama/mlx.
3. **Port (other machines, by RAM tier)** — take what phase 1 learned on this
   machine and bootstrap a *different* machine (64/48/32/24 GB) straight to a
   working `llmrun` setup, without re-running the full matrix there. **This is
   the gap.** Today "porting" means a human reads
   [HARDWARE-RECOMMENDATIONS.md](HARDWARE-RECOMMENDATIONS.md) (which only
   covers 128 GB and 32 GB) and manually edits `models.txt`/`config.sh` on the
   new box. There is no machine-readable output of phase 1, no RAM-tier
   detection, and no tiers between 32 and 128 GB.

## Gaps identified (not yet in any plan)

1. **No RAM-tier detection.** `bin/rt` reads live RAM (`_ram_gb`) but nothing
   classifies "this machine is a 48 GB tier" or picks a starter config from
   that. Every setup is manual, copy-pasted from a markdown table.
2. **No machine-readable "winners" artifact.** `bin/report`/`LEADERBOARD.md`
   are human-readable leaderboards. There's no `profile.json` (or similar)
   that says, per RAM tier: primary model, secondary model, adapter stack,
   `BENCH_CONTEXT`/`BENCH_PARALLEL`/`BENCH_TTL_MINUTES`. Porting currently
   means re-deriving this from prose tables and results by hand every time.
3. **`bin/qualify` (TASKS.md T1) doesn't exist.** Without dominance pruning
   (drop combos strictly worse on both accuracy and speed), "the best combo"
   is a judgment call from reading `LEADERBOARD.md`, not a computed answer —
   which blocks (2) from being generated automatically.
4. **Only 2 of ~5 realistic RAM tiers are documented.** 64 GB, 48 GB, 24 GB
   Macs are common (M-series unified memory steps) and have no guidance at
   all. Extrapolating from 128/32 GB data is unsound — MoE footprints and KV
   cache math don't interpolate linearly (a 20 GB MoE model that's "primary"
   at 128 GB may not leave room for KV cache + adapter overhead at 24 GB).
5. **No bootstrap command for a fresh machine.** `bin/setup` installs tools
   (lms/ollama CLIs, node, etc.) but doesn't touch `models.txt`/`config.sh` or
   trigger `lms get`/`ollama pull` for the tier-appropriate model. There's no
   single command that takes a fresh checkout on a new machine to "models
   downloaded, config.sh tuned, llmrun agents configured" without a human
   reading docs first.
6. **RAM-aware auto-sizing (TASKS.md T3) is a prerequisite, not a nice-to-have,
   for portability** — a fixed `BENCH_PARALLEL=3` baked into `config.sh` is
   wrong on both a 24 GB and a 128 GB box; today someone has to remember to
   hand-edit it per machine (see HARDWARE-RECOMMENDATIONS.md's per-tier
   snippets, which only exist for 128/32 GB).

## Design

### `profile.json` — the machine-readable bench→port bridge

Generated by a new `bin/qualify` (implements TASKS.md T1) from
`results/**/results.csv` + `checks.csv`, grouped by RAM tier:

```json
{
  "generated": "2026-07-04",
  "source_machine": "M5 Max 128GB",
  "tiers": {
    "128": {"primary": {"model": "qwen/qwen3.6-35b-a3b", "adapters": ["aider","cline","interpreter"], "context": 131072, "parallel": 4, "ttl_minutes": 30}, "secondary": {...}},
    "32":  {"primary": {"model": "qwen/qwen3.5-9b", ...}, "secondary": {...}}
  }
}
```

`HARDWARE-RECOMMENDATIONS.md` becomes generated (or at least checked) from
this file instead of hand-maintained prose, the same way `LEADERBOARD.md` is
generated from `bin/report --save`.

### RAM-tier detection + bootstrap

- `bin/hwprofile` (new, small, first thing to build): reports total RAM in GB
  and buckets it into the nearest defined tier (24/32/48/64/128), reusing
  `bin/rt`'s `_ram_gb` helper. Pure detection, no side effects — `bin/rt
  status` gains a tier line, and other scripts can call it.
- `bin/bootstrap-machine` (new, project-local, phase-3 entry point): reads
  `profile.json`, calls `bin/hwprofile` to pick the tier, then: appends the
  tier's model(s) to `models.txt`, writes the `BENCH_CONTEXT`/
  `BENCH_PARALLEL`/`BENCH_TTL_MINUTES` tuning into `config.sh` (dry-run by
  default, `--write` to commit — same convention as `agents config apply`),
  and prints the `lms get <model>` / `ollama pull <model>` command to run.
  Explicitly does **not** auto-download multi-GB models or mutate `config.sh`
  without `--write` — those are exactly the "hard to reverse on someone else's
  machine" actions this project's own conventions (see CLAUDE.md-equivalent
  guidance) say to confirm first.

### New RAM tiers: 64 GB, 48 GB, 24 GB

Need real benchmark data, not extrapolation — tracked as backlog items (see
TASKS.md) to run `bin/bench-overnight --stale` on a 64/48/24 GB machine once
available, then fold results into `profile.json` via `bin/qualify` and
regenerate `HARDWARE-RECOMMENDATIONS.md`'s tier tables. Until then, the doc
should say "not yet benchmarked" for these tiers rather than silently
guessing — no silent extrapolation.

## Sequencing

1. `bin/hwprofile` — detection only, no dependents blocked. **Building now.**
2. `bin/qualify` (T1) — dominance-prune `results/` into ranked combos per tier;
   prerequisite for `profile.json`.
3. `profile.json` generation — `bin/qualify --emit-profile > profile.json`.
4. `bin/bootstrap-machine` — consumes `profile.json` + `bin/hwprofile`.
5. Benchmark runs on 64/48/24 GB hardware as it becomes available; extend
   `profile.json`'s tiers and regenerate `HARDWARE-RECOMMENDATIONS.md`.
6. RAM-aware auto-sizing (T3) folds into `bin/bootstrap-machine`'s config.sh
   write step once T2 (parallel dispatch) exists to make the sizing matter.

## Non-goals

- Auto-running the full bench matrix on the new machine — the point of
  porting is to *skip* that on machines that aren't the primary dev box.
- Syncing `results/` between machines — `profile.json` is the distilled
  artifact that travels; raw run logs stay local.
- Non-Apple-Silicon hardware — out of scope until this project supports a
  runtime that isn't lms/ollama/mlx on macOS.
